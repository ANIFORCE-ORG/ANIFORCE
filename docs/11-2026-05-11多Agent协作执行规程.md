# 2026-05-11 多 Agent 协作执行规程

## 1. 目的

本文件定义 ANIFORCE 客户第一版交付期间的日常协作方式。

目标不是每天重新讨论计划，而是每天按固定流程推进：

1. 项目经理确认当天目标和优先级。
2. 产品经理拆解验收口径。
3. 不同开发职能并行处理前端、后端、API、数据库、部署。
4. 测试工程师验证。
5. 产品经理验收。
6. 项目经理汇总进度、风险和第二天调整。

Codex 在执行时担任总协调 Agent，负责调度这些角色的工作、整合结果、推动当天任务直到完成或遇到明确阻塞。

## 2. 角色定义

### 2.1 项目经理 Agent

职责：

- 维护本周交付目标。
- 每天确认当日任务、优先级、风险和完成标准。
- 控制范围，防止临时需求冲击 P0。
- 每日结束输出：
  - 今日完成
  - 今日未完成
  - 阻塞事项
  - 明日计划
  - 需要用户决策的问题

输入：

- `docs/10-2026-05-11客户第一版交付计划.md`
- 本文件
- 当前代码状态
- 用户最新反馈

输出：

- 当日执行清单
- 状态汇报
- 风险调整建议

### 2.2 产品经理 Agent

职责：

- 把客户第一版目标转成可验收需求。
- 明确每个功能的验收标准。
- 判断功能是否足够客户演示。
- 控制功能体验一致性：
  - 三栏结构
  - 导航一致
  - 文案清楚
  - 不暴露 Demo 瑕疵
  - 不把未完成能力包装成已完成

输出：

- 功能验收清单
- 页面体验问题
- 客户演示脚本调整
- 已知限制说明

### 2.3 前端工程 Agent

职责：

- 修复 Vue/TypeScript 构建错误。
- 维护页面和组件：
  - Dashboard
  - Projects
  - ProjectDetail
  - Campaign
  - CreateCampaign
  - CampaignDetail
  - Material
  - Reports
  - MediaOps / PlatformAccounts
  - Settings
- 统一三栏结构：
  - 左侧 `SidebarNav`
  - 中间业务工作区
  - 右侧 `ChatPanel`
- 修复 UI 交互问题、空白页、路由问题。
- 保证前端生产构建可通过。

输出：

- 前端代码变更
- 前端构建结果
- 页面级验证记录

### 2.4 后端工程 Agent

职责：

- 维护 FastAPI 服务。
- 修复后端启动、路由、异常处理、业务逻辑问题。
- 确保核心 API 可用：
  - `/health`
  - `/api/v1/projects`
  - `/api/v1/campaigns`
  - `/api/v1/materials`
  - `/api/v1/platform/accounts`
  - `/api/v1/platform/connections/meta/config`
  - `/api/v1/media-ops/dashboard`
- 确保日志、错误信息、环境变量符合交付要求。

输出：

- 后端代码变更
- API 冒烟测试结果
- 后端风险说明

### 2.5 API 集成 Agent

职责：

- 检查前端 API client 与后端真实接口是否一致。
- 发现字段不匹配、路径不匹配、请求体不匹配、响应结构不匹配。
- 维护核心业务链路：
  - 项目创建
  - 广告账户绑定
  - Campaign 创建
  - 素材关联 Campaign
  - Agent Action 生成/确认/拒绝
  - 报表数据展示

输出：

- API 对齐问题清单
- 字段兼容修复
- 端到端链路验证结果

### 2.6 数据库与部署 Agent

职责：

- 明确数据库模式：
  - SQLite POC
  - PostgreSQL 生产试点
- 检查 migration 状态。
- 准备数据初始化、演示数据重置、备份恢复方案。
- 明确部署环境变量、端口、CORS、域名、HTTPS、Meta OAuth Redirect。
- 维护启动/停止/健康检查脚本。

输出：

- 数据库交付说明
- 环境变量清单
- 部署配置表
- 备份恢复说明

### 2.7 测试工程 Agent

职责：

- 执行构建测试：
  - `npm run build`
  - `npm exec vite build`
  - `python3 -m compileall backend/app`
- 执行后端接口冒烟测试。
- 执行前端关键路由访问测试。
- 执行业务链路测试：
  - 项目 -> 账户 -> Campaign -> 素材 -> 报表 -> Agent 建议
- 记录缺陷：
  - 阻塞级
  - 高优先级
  - 中低优先级

输出：

- 测试报告
- Bug 清单
- 回归测试结果

### 2.8 发布与交付 Agent

职责：

- 整理交付包。
- 准备客户部署文档。
- 准备账号和环境配置清单。
- 准备客户演示脚本。
- 准备已知限制和下一版本计划。
- 交付前确认版本可回滚。

输出：

- 交付清单
- 部署手册
- 演示脚本
- 验收清单
- 已知限制

## 3. 每日执行流程

### 阶段 0：开工恢复上下文

每天开始先读取：

1. `docs/10-2026-05-11客户第一版交付计划.md`
2. `docs/11-2026-05-11多Agent协作执行规程.md`
3. `git status`
4. 最新构建/测试结果

输出：

- 当日目标
- P0/P1 任务
- 不做事项
- 预计验收标准

### 阶段 1：项目经理确认当日任务

项目经理 Agent 根据本周计划选择当天任务。

格式：

```
今日目标：
- ...

今日 P0：
- ...

今日 P1：
- ...

今日不做：
- ...

验收标准：
- ...
```

如果用户没有新增调整，默认继续执行当天计划，不再重新询问。

### 阶段 2：产品经理拆验收标准

产品经理 Agent 把任务拆成可验收条目。

示例：

```
功能：Campaign 创建链路
验收：
- 页面可进入
- 项目下拉有数据
- 广告账户可选择
- 创建成功后返回本地 Campaign
- 若走 Meta 真实创建，显示 external_campaign_id
- 失败时错误提示可读
```

### 阶段 3：开发 Agent 并行执行

按任务类型分配：

- 前端问题 -> 前端工程 Agent
- 后端逻辑 -> 后端工程 Agent
- 前后端字段/路径 -> API 集成 Agent
- 数据库/部署/权限 -> 数据库与部署 Agent
- 文档/交付材料 -> 发布与交付 Agent

执行原则：

- P0 优先。
- 一次只合并可验证的改动。
- 不扩大范围做无关重构。
- 不覆盖用户已有改动。
- 每个开发任务完成后必须进入测试。

### 阶段 4：测试工程 Agent 验证

测试顺序：

1. 静态/构建测试。
2. 后端健康检查。
3. 核心 API 冒烟。
4. 前端路由检查。
5. 业务链路验证。
6. 回归刚修过的问题。

测试输出格式：

```
测试通过：
- ...

测试失败：
- ...

阻塞：
- ...

建议：
- ...
```

### 阶段 5：产品经理验收

产品经理 Agent 按验收标准判断：

- `通过`
- `有条件通过`
- `不通过`

判断口径：

- 客户是否能看懂。
- 演示是否稳定。
- 页面是否符合系统结构。
- 未完成能力是否有明确标识。
- 是否存在会破坏客户信任的数据或文案。

### 阶段 6：项目经理收口

项目经理 Agent 汇总：

```
今日完成：
- ...

今日剩余：
- ...

风险：
- ...

需要用户决策：
- ...

明日建议：
- ...
```

如果当天任务已完成，才向用户做完整汇报。

如果遇到以下阻塞，必须提前向用户沟通：

- 需要外部账号、密钥、域名、服务器权限。
- 需要联网安装依赖或访问外部 API，但当前环境无法执行。
- 发现会改变交付范围的架构问题。
- 发现数据或密钥安全风险。
- 需要用户确认是否使用 Demo Mode 还是生产登录模式。

## 4. 状态流转

每个任务使用以下状态：

- `Backlog`：待排期
- `Ready`：今日可做
- `In Progress`：开发中
- `Code Review`：自检/代码检查
- `Testing`：测试中
- `Product Acceptance`：产品验收
- `Done`：完成
- `Blocked`：阻塞
- `Deferred`：延期

状态流转：

```
Backlog -> Ready -> In Progress -> Code Review -> Testing -> Product Acceptance -> Done
                                      |             |                    |
                                      v             v                    v
                                   Blocked       Blocked              Blocked
```

## 7. 与用户的沟通原则

默认行为：

- 每天按计划自动推进。
- 不因普通细节反复打断用户。
- 当天任务完成后做完整汇报。
- 本地沙箱内可完成的代码、测试、构建、文档、演示数据整理，默认由 Codex 自主推进到完成。

必须打断用户的情况：

- 需要密钥、账号、服务器、域名、客户配置。
- 有交付范围变更。
- 有安全风险。
- 有不可绕过的技术阻塞。
- 需要决定 Demo Mode 还是生产模式。

### 7.1 本地沙箱自主执行授权

用户授权后，Codex 默认在本地工作区内自主完成完整开发闭环：

1. 读取代码和文档。
2. 修改前端、后端、API、数据库脚本和交付文档。
3. 运行构建、测试、健康检查和本地服务。
4. 修复发现的问题。
5. 重复开发和测试，直到当天任务完成或出现真正外部阻塞。
6. 更新进展文档。
7. 当天任务完成后再统一向用户汇报。

本地沙箱内默认不需要用户逐项确认的事项：

- 修复 TypeScript、Vue、Python、FastAPI 代码问题。
- 修改接口字段、类型、路由和页面结构。
- 增加或调整本地测试脚本。
- 增加或调整交付文档。
- 调整 Demo 数据和演示数据，前提是不删除用户明确要求保留的数据。
- 启动和停止本地开发服务。
- 运行本地构建、编译、接口测试、健康检查。

仍然必须请求用户确认的事项：

- 使用真实客户服务器、云平台、域名、DNS、HTTPS 证书。
- 写入或修改生产数据库。
- 使用真实客户 Meta / Google / TikTok 账号和密钥。
- 触发真实广告投放、真实消耗预算或修改真实线上广告。
- 推送到远程仓库、打生产 tag、发布到客户环境。
- 安装需要联网下载的新依赖，且当前权限或网络策略要求用户批准。
- 删除大量数据、重置数据库、覆盖备份、执行不可逆操作。
- 发现需求范围需要改变，或本周交付目标需要降级。

如果技术阻塞可以通过本地修改、降级实现、Mock、配置调整、测试补充解决，Codex 应先自行处理，不提前打断用户。

如果阻塞依赖外部条件，Codex 应把问题标记为 `Blocked`，并一次性说明：

- 阻塞是什么。
- 为什么本地无法绕过。
- 需要用户提供什么。
- 提供后我会继续做什么。
- 是否有临时演示替代方案。

汇报格式：

```
今日完成：

验证结果：

未完成/风险：

需要你确认：

下一步：
```

## 8. 执行约束

- 不覆盖用户未确认的改动。
- 不把未完成能力包装成已完成。
- 不跳过测试直接宣布完成。
- 不新增与本周交付无关的大重构。
- 不把密钥写入代码或文档。
- 不在客户交付文档中暴露生产密码。
- 遇到网络、权限、密钥、部署环境问题时，及时标记为 `Blocked`。
