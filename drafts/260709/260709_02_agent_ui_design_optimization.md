# ANIFORCE Agent 工作台交互设计重构方案

**版本**：v2.0
**重构日期**：2026-07-10
**适用范围**：首页 Agent、消息时间线、Workspace、工具运行、业务审批、对象引用
**目标**：不是让界面“更像 AI”，而是让用户更快、更稳、更可控地完成广告业务任务。

---

## 0. 结论先行

当前实现的主要问题不是缺少动画，也不是工具卡片不够精致，而是界面同时存在多套竞争性的交互模型：

- 对话流既展示回答，又展示推理、工具、任务和审批；
- Workspace 既是结果画布，又是工具结果容器、任务面板和审批入口；
- HITL 弹窗与 Workspace 审批并存；
- “工具执行”“任务阶段”“下一步动作”在多个区域重复表达；
- Workspace 默认常驻，即使没有值得查看的对象也占据空间。

这会让用户反复判断：**我现在应该看中间、看右边，还是等弹窗？**

新版只保留一个稳定心智模型：

```text
Chat      = 说明意图、给出判断、接受指令
Workspace = 查看、选择、编辑、比较业务对象
Run Trace = 回答“Agent 做了什么”，默认收起
Approval  = 在将发生变更的对象旁完成确认
```

一句话原则：

> **对话负责决策，Workspace 负责对象，运行轨迹负责信任，审批只保留一个主入口。**

本方案基于当前项目真实实现，而不是抽象概念设计。重点审阅了：

- `frontend/packages/main-app/src/pages/Home.vue`
- `frontend/packages/main-app/src/components/agent/MessageView.vue`

- `frontend/packages/main-app/src/components/agent/ToolCallView.vue`
- `frontend/packages/main-app/src/components/agent/HITLDialog.vue`
- `frontend/packages/main-app/src/components/agent/TaskStatusPanel.vue`
- `frontend/packages/main-app/src/components/agent/workspace/LiveWorkspaceShell.vue`
- `frontend/packages/main-app/src/components/agent/workspace/WorkspaceRenderer.vue`
- `frontend/packages/main-app/src/composables/useHomeAgentSession.ts`
- `frontend/packages/main-app/src/api/agent.ts`
- Workspace、AG-UI、HITL、Timeline、Session State 相关设计文档

当前项目已经具备以下基础能力：

1. Agents SDK 原生消息、reasoning、tool call、tool result 与审批事件接入；
2. 项目、计划、素材等业务对象向 Workspace 投影；
3. Workspace 选择实体、`@mention`、编辑审批和业务组件复用；
4. 流式状态、任务状态、工具运行状态与 session 管理；
5. Workspace 宽度和收起状态持久化。

因此，本次不建议重做协议或建立新 UI 框架，而应整理现有能力的产品边界。

## 2. 第一性原理：用户真正要完成什么

ANIFORCE 的核心用户不是来观察 Agent 如何思考，而是要完成以下工作：

1. **理解现状**：项目、计划、素材、投放数据发生了什么；
2. **做出决策**：选哪个对象、采用什么策略、是否继续；
3. **产生业务对象**：创建或修改项目、计划、素材和关联关系；
4. **控制风险**：在副作用发生前看清对象、差异和影响；
5. **继续推进**：知道下一步是什么，并能立即执行。

由此得到五个不可妥协的设计指标：

| 指标 | 用户问题 | 设计要求 |
|---|---|---|
| 可理解 | “现在发生了什么？” | 当前状态必须一眼可见 |
| 可行动 | “我下一步能做什么？” | 主动作明确且就近出现 |
| 可控制 | “执行前我能检查和修改吗？” | 变更前可审阅、可编辑、可拒绝 |
| 可追溯 | “它依据什么、做了什么？” | 过程可查看，但不抢占主内容 |
| 可恢复 | “失败或误操作后怎么办？” | 错误可定位、可重试、可修正 |

“高级感”不是渐变、发光和呼吸动画，而是：

- 页面稳定，不随事件频繁跳动；
- 信息不重复；
- 状态变化可预测；
- 操作结果与触发位置有因果连续性；
- 系统只在必要时打断用户。

## 3. 当前实现的根因诊断

### 3.1 一个运行被拆成太多视觉对象

同一轮任务可能同时出现：

- 中间消息中的 Thinking；
- 多个工具调用卡；
- 独立 Activity 消息；
- 右侧任务阶段；
- Workspace 底部活动时间线；
- Agent 最终回答。

这些对象来自不同技术事件，但对用户而言都只是同一件事：**Agent 正在完成我的任务**。

**根因**：界面直接映射底层事件，而不是先聚合为用户任务。

### 3.2 Chat 与 Workspace 内容职责重复

项目列表、工具结果、业务摘要可能同时出现在消息与 Workspace；Workspace 还保留通用 JSON 工具结果兜底。

**结果**：用户不知道哪个版本是当前、完整、可操作的权威对象。

### 3.3 Workspace 被当作固定第三栏，而不是任务画布

当前首页无论是否存在业务对象，都为 Workspace 保留 56px 或更宽区域，并展示“等待业务对象”。

**问题**：空 Workspace 没有用户价值，却持续压缩对话区；自动展开又可能导致布局突然变化。

### 3.4 审批存在竞争入口

项目中同时存在 `HITLDialog.vue` 和 Workspace 内的审批视图。若同一业务动作可能在弹窗或 Workspace 完成，用户会失去位置记忆。

### 3.5 `@mention` 把“选择上下文”误做成“醒目的按钮”

旧方案建议让每张卡常驻一个呼吸的 `@` 按钮。实际任务是把对象加入当前输入上下文，并不值得持续抢占视觉注意力。

### 3.6 视觉优化方向偏离任务价值

旧方案重点包含：渐变状态徽章、发光、脉冲、旋转、抖动、箭头引导和 Toast。这些效果不能解决信息重复与入口竞争，反而增加噪声，并可能产生无障碍和性能问题。

## 4. 业界经验转译为 ANIFORCE 原则

本方案只吸收能够解释为产品原则的模式，不机械照搬视觉外观。

### 4.1 Chat + Canvas / Artifact 模式

OpenAI Canvas 和 Claude Artifacts 的共同点是：

- 对话保留自然语言协作；
- 长内容、代码、文档或可操作成果进入独立工作面；
- 用户可在工作面直接编辑，并继续通过对话发出指令；
- 工作面因“出现了值得持续操作的成果”而打开，而不是默认常驻。

对 ANIFORCE 的转译：

> 只有当出现需要持续查看、选择、编辑、比较或审批的业务对象时，Workspace 才成为主舞台。

### 4.2 渐进式披露

专业产品不会把所有模型过程、参数和工具输出默认展示。默认层只回答当前任务，审计层按需展开。

对 ANIFORCE 的转译：

- 默认展示业务状态，不展示底层 SDK 事件；
- 用户需要判断可靠性或排查问题时，再查看运行轨迹；
- 原始参数、原始结果只在开发者模式出现。

### 4.3 Human-AI Interaction Guidelines

成熟 AI 交互强调：让用户理解能力边界、显示当前状态、支持有效修正、允许忽略或撤销、在失败时提供恢复路径。

对 ANIFORCE 的转译：

- 不使用“AI 正在分析中”这类无法说明进度的泛化状态；
- 把状态写成业务动作，如“正在读取 12 个素材”“等待你确认预算变更”；
- 用户纠正对象或参数后，不必重启整个流程；
- 高风险动作必须显示影响范围。

### 4.4 动效与无障碍规范

动效用于解释空间、因果和状态变化，不用于持续吸引注意力。所有非必要动效应兼容 `prefers-reduced-motion`。

对 ANIFORCE 的转译：

- 禁止常驻呼吸、发光和无限脉冲；
- 禁止错误抖动；
- 允许一次性的展开、聚焦和完成过渡；
- 颜色不能是唯一状态编码。

## 5. 新的信息架构

### 5.1 页面只保留四个功能层

```text
┌────────────┬──────────────────────────────┬─────────────────────────┐
│ Sessions   │ Conversation                 │ Workspace               │
│            │                              │                         │
│ 会话导航    │ 用户意图 / Agent 判断         │ 业务对象 / 草稿 / 审批     │
│            │ Run Summary（按轮聚合）        │                         │
│            │ Composer                     │                         │
└────────────┴──────────────────────────────┴─────────────────────────┘

全局层：轻量通知、阻断性系统错误
```

| 区域 | 只负责 | 不负责 |
|---|---|---|
| Sessions | 会话创建、切换、命名、删除 | 当前任务详情 |
| Conversation | 意图、解释、结论、问题、运行摘要 | 大型业务列表、复杂表单 |
| Workspace | 对象查看、选择、编辑、比较、审批 | 重复 Agent 最终回答 |
| Composer | 指令输入、上下文对象、附件 | 任务阶段展示 |
| Global | 系统级通知与故障 | 普通业务成功反馈 |

### 5.2 权威内容唯一原则

每类信息必须有且只有一个权威展示位置：

| 信息 | 权威位置 |
|---|---|
| Agent 结论与解释 | Conversation |
| 项目/计划/素材完整内容 | Workspace |
| 当前输入引用的对象 | Composer context chips |
| 当前运行总体状态 | 当前轮 Run Summary |
| 工具明细 | Run Trace 抽屉 |
| 业务变更审批 | Workspace 对象内 |
| 系统故障 | Global error / 当前轮错误摘要 |

## 6. 核心交互模型：一轮对话 = 一个 Run Group

不要把 reasoning、tool call、tool result 和 answer 渲染成同级消息。前端应按 `runId` 聚合为一轮任务：

```text
Run Group
├─ User request
├─ Run status summary
├─ Optional workspace projection link
├─ Assistant answer
└─ Expandable run trace
```

### 6.1 运行中的默认形态

```text
你：分析 @德国新品项目 的素材准备情况

ANIFORCE
正在检查项目素材                       8 秒   [停止]
已读取项目详情 · 正在比对 12 个素材

└─ 查看运行轨迹
```

规则：

- 只显示一张运行摘要，不逐条增加工具卡；
- 摘要动词来自业务映射，不显示 `get_project_detail`；
- 状态在原位置更新，不新增“开始/完成”两张卡；
- 超过 8 秒可显示经过时间，但不伪造百分比；
- 用户可停止运行；停止后保留已完成步骤。

### 6.2 完成后的默认形态

```text
ANIFORCE
当前 12 个素材中，8 个可直接使用，3 个缺少德语文案，1 个尺寸不符合要求。
建议先补齐 3 个文案，再生成 9:16 版本。

[查看右侧素材]  [补齐文案]

已检查项目、素材和规格 · 4 个步骤 · 11 秒  [查看轨迹]
```

规则：

- 最终回答是主内容；
- 工具过程压缩为一行事实；
- 业务对象进入 Workspace，不在消息里复制完整列表；
- 最多展示 1 个主动作和 1 个次动作；
- “查看轨迹”不是一个大卡片。

### 6.3 运行轨迹展开形态

```text
运行轨迹                                      [收起]
✓ 读取项目详情                               0.4s
✓ 查询项目素材（12）                          1.2s
✓ 对照投放规格                                0.8s
✓ 生成建议                                   2.1s

模型说明  [展开]
```

轨迹层级：

1. 默认：用户友好的步骤名称、状态、耗时、关键数量；
2. 二级：错误原因、重试次数、数据来源；
3. 开发者模式：工具技术名、参数、原始结果、事件 ID。

不建议默认展示完整 reasoning。若产品决定开放，应命名为“模型说明”或“分析过程”，并明确它是系统生成的过程信息，不等同于可验证事实。

## 7. Workspace 设计

### 7.1 Workspace 不是固定侧栏，而是上下文画布

Workspace 有四种状态：

| 状态 | 页面行为 |
|---|---|
| `closed` | 不占宽度，对话为主 |
| `peek` | 仅显示 48px 对象入口和状态，不展示空内容 |
| `open` | 展示对象，可调整宽度 |
| `focus` | 审批、复杂编辑或比较时获得主要宽度 |

### 7.2 打开规则

**自动打开**仅发生在：

1. 用户明确要求“打开、查看、编辑、比较”；
2. 产生了需要继续操作的对象或草稿；
3. 需要用户审批业务变更；
4. 结果必须依赖视觉内容理解，如素材预览。

**不自动打开**：

- 简单问答；
- 单值查询；
- 只需一句摘要的成功结果；
- 后台工具执行；
- Workspace 已有对象但本轮与其无关。

### 7.3 防止布局惊跳

- 用户正在阅读历史消息时，不自动改变布局；
- 新投影到达时显示内联入口：“已准备 12 个素材”，由用户打开；
- 只有当前视口接近底部且本轮明确需要 Workspace 时才自动打开；
- 用户手动收起后，本次会话内不再次自动展开，审批除外；
- 移动端不做第三栏，使用全屏 sheet / 页面切换。

### 7.4 Workspace Header

```text
素材 · 德国新品项目                     12 个
[对象面包屑]               [刷新] [更多] [关闭]
```

必须包含：

- 对象类型与名称；
- 数据新鲜度或数量；
- 与当前会话的关联；
- 明确关闭入口；
- 若有未保存编辑，显示状态。

不要使用泛化标题“工作台”作为唯一标题。

### 7.5 Workspace 内部结构

```text
Header
Context / Filter bar（需要时出现）
Primary object canvas
Sticky action bar（只有可行动时出现）
Optional activity drawer
```

Activity 不应永久占据 Workspace 底部。当前 `LiveWorkspaceShell` 中的“活动 + 下一步”固定 footer 建议改为：

- 普通查看：隐藏；
- 运行中：顶部轻量状态条；
- 有动作：底部 sticky action bar；
- 需审计：用户展开 activity drawer。

### 7.6 空状态

删除长期占位的“等待业务对象”。无对象时 Workspace 应关闭；用户主动打开空 Workspace 时才显示：

```text
这里会显示你正在查看或编辑的业务对象。
[浏览项目] [浏览素材]
```

## 8. 业务审批：只保留一个主入口

### 8.1 原则

审批不是“系统弹出确认框”，而是用户对一个即将发生的业务变更进行审阅。

所有可在 Workspace 表达的业务审批，都在 Workspace 完成。`HITLDialog` 只保留给无法建立业务对象视图的系统级权限确认或兼容性兜底。

### 8.2 审批画布结构

```text
修改广告计划                               待确认

变更摘要
预算       ¥50,000  →  ¥80,000
市场       德国     →  德国、法国
开始日期   07-15    →  07-12

影响
• 日预算上限增加 60%
• 将新增法国市场投放

[返回修改]                         [确认修改]
```

必须展示：

- 动作对象；
- 变更前后差异；
- 影响范围；
- 风险提示；
- 主按钮使用具体动词，如“确认删除 3 个素材”；
- 拒绝后保留草稿，可继续修改。

### 8.3 风险分级

| 风险 | 示例 | 交互 |
|---|---|---|
| 低 | 查询、筛选、预览 | 不审批 |
| 中 | 创建草稿、修改未发布对象 | Workspace 内单次确认 |
| 高 | 发布、删除、预算变更、解除关联 | 差异 + 影响 + 明确确认 |
| 极高 | 批量删除、跨组织操作 | 二次确认或输入对象名 |

禁止对所有写操作使用同样强度的弹窗，否则用户会形成确认疲劳。

### 8.4 成功与失败

成功不再弹 Toast 后立即清空上下文，而是在原审批位置转为结果：

```text
✓ 广告计划已更新                         [查看计划]
```

失败则保持表单与用户编辑：

```text
未能更新：预算超过账户上限。
[调整预算] [重试]
```

## 9. 上下文引用与 `@mention`

### 9.1 正确心智模型

`@mention` 是“把对象加入当前请求上下文”，不是社交网络式提及，也不是每张卡都需要闪烁的功能入口。

### 9.2 三种添加方式

1. **选择后添加**：列表支持多选，工具栏出现“加入对话”；
2. **对象菜单添加**：卡片/行的更多菜单中选择“在对话中引用”；
3. **输入框搜索添加**：输入 `@` 打开跨对象搜索。

桌面端可保留卡片 hover 快捷动作，但不要常驻呼吸动画。

### 9.3 Composer 中使用结构化 chips

不要把引用只写成普通文本 `@test111`。视觉上应形成可删除、可检查的上下文 chip：

```text
[项目 · 德国新品 ×] [素材 · 3 个 ×]
┌─────────────────────────────────────────────┐
│ 比较这些素材并给出投放建议……                 │
└─────────────────────────────────────────────┘
```

发送给后端时继续使用已有 `selected_entities` / `mentions` 结构，不依赖模型解析名称。

### 9.4 反馈

- 添加后：chip 进入 Composer，即为主要反馈；
- 卡片短暂显示勾选状态 600ms；
- 不额外弹 Toast，除非操作发生在 Composer 不可见区域；
- 对象失效时 chip 显示“不可用”，发送前要求移除或替换。

## 10. Composer 重构

当前输入框周围同时存在模式切换、快速标签、附件、语音、发送和 `@`。建议将 Composer 简化为稳定三层：

```text
Context chips（有上下文时出现）
Text input
Attachment / scope                               Send / Stop
```

### 10.1 取消显式“聊天 / 项目管理”模式切换

用户表达的是目标，不应先选择 Agent 模式。现有 `intentModes` 可继续作为后端 hint，但由系统根据输入和当前对象推断；只有路由或权限显著改变时才让用户选择模式。

### 10.2 快速开始改为任务模板

首页建议保留 3–4 个真实业务入口：

- 分析一个项目；
- 创建投放计划；
- 评估一组素材；
- 查看异常投放。

点击后先让用户选择必要对象或补齐最少信息，不直接发送宽泛 prompt。

### 10.3 运行时发送按钮变为停止

运行期间不应只是禁用输入：

- 主按钮切换为“停止”；
- 输入框仍可编辑下一条消息，但提示“将在当前任务结束后发送”，或首版直接保持可编辑、不允许提交；
- 用户停止后清晰显示哪些步骤已完成。

---

## 11. 状态、反馈与文案规范

### 11.1 状态只保留五类

```text
idle / running / needs_action / completed / failed
```

SDK 的更多内部状态可保留在数据层，但不要一一暴露为视觉状态。

### 11.2 状态文案公式

```text
[正在做什么] + [对象或数量] + [用户是否需要行动]
```

推荐：

- 正在读取“德国新品”项目；
- 正在比较 12 个素材；
- 已生成广告计划草稿，等待你确认；
- 3 个素材未能关联，可重试。

避免：

- AI 正在分析中；
- Agent 正在处理；
- 调用了 3 个工具；
- operation completed。

### 11.3 反馈层级

| 反馈 | 表现 |
|---|---|
| 即时局部反馈 | 按钮状态、行内状态 |
| 业务结果 | 原对象或 Run Group 原位更新 |
| 跨区域变化 | 一次性内联提示与聚焦 |
| 系统级异常 | 全局 banner / error boundary |
| 后台完成 | 通知中心，可选 Toast |

Toast 不能替代持久结果，也不能承载审批和关键错误。

---

## 12. 视觉设计规范

### 12.1 视觉层级

1. **Level 0：页面结构**——背景与栏位，不使用阴影堆叠；
2. **Level 1：内容组**——Run Group、Workspace section；
3. **Level 2：可交互对象**——卡片、表格行、表单；
4. **Level 3：临时浮层**——菜单、tooltip、picker；
5. **Level 4：阻断层**——极少数系统 modal。

当前大量 `rounded-xl + shadow + border + 彩色底` 的组合应收敛。边框、底色、阴影最多选择两种用于同一层级。

### 12.2 色彩

- 中性色承载 80% 界面；
- 品牌色只表示主动作、选中和焦点；
- 绿色只表示成功，红色只表示错误/危险，琥珀色表示需要注意；
- 运行中优先使用中性 spinner/progress，不使用蓝色发光；
- 状态同时包含图标与文字，不能只靠颜色。

### 12.3 排版

- Agent 正文：14–15px，行高 1.65；
- 辅助信息：12px，行高 1.5；
- 不建议在核心业务区大量使用 10px/11px；
- 技术 ID 默认截断，完整值在复制或详情中展示；
- 中文文案避免全大写英文状态。

### 12.4 动效

允许：

- Workspace 打开/关闭：180–240ms；
- 内容淡入与位置变化：120–180ms；
- 完成状态一次性过渡：不超过 240ms；
- 聚焦高亮：一次，800–1200ms 后消失。

禁止：

- 无限呼吸；
- 无限发光；
- 错误抖动；
- 多个 spinner 同屏；
- 工具图标持续旋转；
- 通过动画强迫用户查看右侧。

必须支持：

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

### 12.5 响应式

| 宽度 | 结构 |
|---|---|
| ≥ 1440px | Sessions + Chat + Workspace |
| 1024–1439px | 窄 Sessions + Chat + 可覆盖 Workspace |
| < 1024px | Chat 主页面，Workspace 全屏 sheet |
| < 640px | Sessions 抽屉，Composer 底部固定 |

不要用固定最小 520px Workspace 把中等屏幕的 Chat 压得过窄。

## 13. 关键场景交互稿

### 场景 A：简单查询

**用户**：这个项目预算多少？

- 若当前已有唯一选中项目，直接回答；
- 不打开 Workspace；
- 不显示工具卡；
- 回答底部只显示“已读取项目详情 · 0.5s”。

### 场景 B：查看项目列表

**用户**：列出最近活跃的项目。

1. 当前 Run Summary 显示“正在查询活跃项目”；
2. 完成后 Workspace 打开项目列表；
3. Chat 只回答：“找到 8 个活跃项目，按最近更新时间排序。”；
4. Chat 提供“比较预算”主动作；
5. 用户在 Workspace 选择项目并“加入对话”。

### 场景 C：创建项目

**用户**：创建一个德国休闲游戏项目，预算 5 万。

1. Agent 补问真正缺失的必填项；
2. Workspace 进入项目草稿表单；
3. Chat 说明已填内容与待确认风险；
4. 用户可直接修改表单；
5. 点击“创建项目”进入一次审批；
6. 成功后同位置切换为项目详情，不再弹第二个成功弹窗。

### 场景 D：高风险预算修改

**用户**：把这个计划预算提升到 20 万。

1. Workspace 打开变更 diff；
2. 显示原预算、新预算、增幅和账户上限影响；
3. 主按钮为“确认将预算改为 ¥200,000”；
4. Chat 不再重复一张审批卡；
5. 执行失败时保留用户编辑值。

### 场景 E：长任务

**用户**：分析全部素材并给出德国市场优化方案。

1. 单一 Run Summary 原位更新；
2. 显示业务阶段，不显示工具流瀑布；
3. 用户可展开轨迹或停止；
4. 素材结果逐步投影到 Workspace，但不抢焦点；
5. 完成后 Chat 给结论，Workspace 保留可筛选结果。

### 场景 F：错误恢复

如果关联素材时 10 个成功、2 个失败：

```text
已关联 10 个素材，2 个失败。
失败原因：素材已被删除。
[移除失效项] [重试其余操作]
```

禁止只显示“工具调用失败”或原始异常堆栈。

## 14. 与当前代码的最小改造路径

本方案不要求更换 Vue、Tailwind、Agents SDK 或现有业务组件。

### Phase 1：统一信息层级（P0）

目标：先消除重复与入口竞争。

1. 在 `useHomeAgentSession.ts` 增加前端派生的 `runGroups`，按 `runId` 聚合消息、工具、reasoning、结果和状态；
2. 将 `MessageView.vue` 的工具与 thinking 展示收敛为单一 `RunSummary/RunTrace`；
3. 查询结果只在 Workspace 展示完整业务对象，Chat 只保留摘要与入口；
4. 业务审批统一进入 `WorkspaceRenderer.vue`；
5. `HITLDialog.vue` 限定为系统级兜底；
6. 删除 Workspace 空占位常驻逻辑，无对象时关闭。

建议组件边界：

```text
components/agent/run/
  RunGroup.vue
  RunStatus.vue
  RunTrace.vue
  RunActions.vue
```

只有在拆分能降低 `MessageView.vue` 当前 1000+ 行复杂度时才新建，不建立新的通用设计系统。

### Phase 2：Workspace 状态机（P0）

1. 将 `workspaceCollapsed: boolean` 升级为 `closed | peek | open | focus`；
2. 增加打开原因 `user | projection | approval | restore`；
3. 记录用户手动关闭，防止自动反复打开；
4. 移除 `LiveWorkspaceShell` 固定活动 footer，改为条件状态条和 action bar；
5. 中屏幕使用 overlay Workspace。

### Phase 3：结构化上下文（P1）

1. Composer 展示 selected entity chips；
2. 卡片动作统一为“加入对话”；
3. 输入 `@` 使用同一对象搜索源；
4. 发送时直接提交结构化 mentions；
5. 移除常驻呼吸 `@` 按钮和重复 Toast。

### Phase 4：审批与错误恢复（P1）

1. 为 update/delete/publish 增加 diff 与 impact presentation；
2. 按风险决定确认强度；
3. 支持失败后保留草稿和局部重试；
4. 成功状态在原 Workspace 位置完成闭环。

### Phase 5：视觉与无障碍（P2）

1. 收敛字号、圆角、边框和状态色；
2. 全局支持 reduced motion；
3. 键盘可访问：Workspace、轨迹、审批、对象选择；
4. 状态更新使用 `aria-live="polite"`，错误使用 `role="alert"`；
5. 验证窄屏与 200% zoom。

## 15. 不做清单

为避免再次过度设计，明确不做：

- 不为每个工具持续维护手工 UI 流程；
- 不把技术工具名作为主文案；
- 不默认展示原始工具输入输出；
- 不默认展示完整 reasoning；
- 不同时保留 Workspace 审批和业务审批弹窗；
- 不为“高级感”增加发光、渐变、呼吸和抖动；
- 不自动锁死 Workspace 使用户无法收起；
- 不创建“自动 / 常驻展开 / 常驻收起”三档复杂偏好；
- 不把所有查询结果同时复制到 Chat 和 Workspace；
- 不新增独立 Agent 专用业务组件，继续复用 SaaS 组件。

## 16. 验收标准

### 16.1 用户任务指标

| 指标 | 目标 |
|---|---|
| 首次理解当前状态 | 5 秒内可说出系统正在做什么 |
| 找到主动作 | 3 秒内 |
| 查询结果重复 | Chat 与 Workspace 不出现完整重复对象 |
| 审批入口 | 每个业务动作只有一个主入口 |
| 错误恢复 | 错误旁提供至少一个明确恢复动作 |
| 长任务控制 | 用户始终可查看状态并停止 |

### 16.2 界面检查

- 同屏最多一个持续 loading 动画；
- 同一运行只有一个主状态；
- Workspace 无业务对象时不占据主要宽度；
- Workspace 自动打开不打断历史阅读；
- 所有高风险审批显示对象、差异、影响和具体动作；
- `@mention` 添加后在 Composer 有可见 chip；
- 关闭 Workspace 后不会被普通投影立即强制打开；
- 不依赖颜色表达成功、失败和待确认；
- reduced motion 下功能完整；
- 键盘可完成发送、展开轨迹、选择对象和审批。

### 16.3 技术检查

- 不改变 Agents SDK 原生事件协议；
- 聚合逻辑基于稳定 `runId/toolCallId`；
- Workspace 继续复用现有业务组件；
- 原始工具结果仅在开发者模式加载或展示；
- 前端无新增无必要依赖；
- 不引入大范围无关重构。

## 17. 建议先制作的三张原型

在写代码前，只需要验证三张高价值原型：

1. **查询完成态**：Chat 摘要 + Workspace 项目列表 + Run Trace；
2. **长任务运行态**：单一 Run Summary + 增量 Workspace；
3. **高风险审批态**：Workspace diff + impact + 失败恢复。

若这三张原型能让 5 位目标用户在无讲解情况下完成任务，再进入实现。不要先制作完整视觉设计系统。

## 18. 参考依据

本方案参考的不是单一产品外观，而是以下成熟模式：

- OpenAI Canvas：对话与可编辑工作面的职责分离；
- Anthropic Artifacts：成果对象进入独立、可持续操作的空间；
- Microsoft Human-AI Interaction Guidelines：能力边界、状态反馈、有效修正、可忽略与可恢复；
- Nielsen Norman Group 渐进式披露：默认展示必要信息，复杂细节按需出现；
- W3C/WCAG 动效与状态可感知原则：减少非必要动画，并确保状态不只依赖视觉装饰。

最终判断标准始终是 ANIFORCE 的业务任务，而不是“像 ChatGPT”或“像 Claude”。
